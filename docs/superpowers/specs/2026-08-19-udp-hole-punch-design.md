# 设计规格：UDP 打洞 + QUIC 直连传输（P2P 数据通道升级）

> 日期: 2026-08-19 | 分支: `feat/desktop-app` | 状态: 待实施
> 决策方式: 与 kentnf 逐项讨论确定（失败降级/通道复用/QUIC 协议）

---

## 一、背景与目标

fan-files P2P 传输（magic-wormhole）当前数据通道为 **TCP 打洞 + relay 兜底**。
问题：TCP 打洞成功率低（尤其学校级对称 NAT），打洞失败时数据经 47.94.142.52:4001
中继，占用阿里云流量（计费成本高、带宽有限）。

**目标**：引入 **UDP 打洞**（成功率约 70%，业界天花板）提升直连比例，数据尽量
不占公网服务器带宽；打洞失败自动降级现有 relay，保证可用性。数据通道从 TCP
升级为 **QUIC（quinn）**，在打通的 UDP socket 上直连。

**明确不做（v1）**：不替换 magic-wormhole 配对/加密层；不引入 libp2p；不做持续
同步；不删除 relay（保留为兜底）。

## 二、已确认决策（含理由）

| # | 决策 | 选择 | 理由 |
|---|------|------|------|
| 1 | 失败降级 | 自动降级现有 relay | 保可用性；成功率 ~70% 直连、30% relay 可接受 |
| 2 | 地址交换通道 | 复用 magic-wormhole 的 Wormhole 通道 | 已认证+加密，交换 UDP 地址/证书指纹零新安全面 |
| 3 | 数据协议 | QUIC（quinn）在打通的 UDP socket 上 | 自带可靠传输/流控/拥塞/TLS，成熟、代码量小 |
| 4 | 架构 | 自写 UdpPuncher + QuicLink，不引 libp2p | 成功率由 NAT 决定而非库；自写可控、依赖小 |
| 5 | 传输复用 | 保留 tar 打包/解包/进度回调 | send/get 业务逻辑不动，只换底层传输 |

## 三、架构

```
数据方/请求方（同构，双向对称）
┌─────────────────────────────────────────────┐
│  transfer.rs（现有）                         │
│  ├─ Wormhole 配对（复用，已认证加密）          │
│  │    ├─ rendezvous 交换配对码/密钥/公钥       │
│  │    └─ Wormhole 通道：交换 UDP 地址 + 证书指纹 │
│  ├─ UdpPuncher（新）                         │
│  │    ├─ 绑定本地 UDP socket（随机端口）        │
│  │    ├─ 向对方公网地址发打洞包（重试+超时）     │
│  │    └─ 打通后返回可用的 UdpSocket            │
│  ├─ QuicLink（新）                           │
│  │    ├─ quinn 在打通的 socket 上建 QUIC 连接  │
│  │    ├─ 证书指纹经 Wormhole 通道交换（防 MITM）│
│  │    └─ 流式传输（复用 send/get 的 tar 逻辑）  │
│  └─ 失败自动降级 relay（现有 magic-wormhole）   │
└─────────────────────────────────────────────┘
```

**Wormhole 通道职责**：不承担数据，只交换元数据（UDP 地址/证书指纹）——带宽占用 KB 级。
**数据面**：打洞成功 → QUIC 直连；失败 → relay 兜底。

## 四、打洞流程（UdpPuncher）

```
① 双方各绑一个 UDP socket（随机端口）
② 经 Wormhole 通道交换各自的"本地 UDP socket 地址"
③ 双方同时向对方地址发打洞包（每 100ms 一发，最多 N 次）
④ 收到对方包 → 双方 NAT 都开了洞 → 打洞成功
⑤ 超时未通 → 失败 → 降级 relay
```

**NAT 原理**：我方发向对方公网出口的包让 NAT 记住"我要和 X 通信"；对方同时发来，
NAT 放行入站——两个洞互开即直连。**对称 NAT 下可能失败**（学校网络），自动降级。

**打洞参数（可调，默认值）**：
- 打洞包间隔：100ms
- 最大尝试次数：30（即 3 秒）
- 打洞包内容：随机 nonce + 发送方标识（用于识别对方是否收到）

## 五、数据通道（QuicLink）

- quinn 在打通的 `UdpSocket` 上建 QUIC 连接（自带 TLS 1.3 加密）
- **证书指纹经 Wormhole 通道预交换**——双方验证对方证书指纹一致才握手（防中间人）
- 复用现有 tar 打包/解包 + 进度回调（send/get 业务逻辑基本不动，只换底层传输）

## 六、失败降级

```
UdpPuncher 超时/失败 → 自动降级现有 magic-wormhole relay 传输
（完整保留：配对/加密/进度/解包全复用）
```

**可观测性**：日志打印 `连接: UDP直连` / `连接: relay中继`，供排障与统计直连率。

## 七、错误处理

| 场景 | 处理 |
|------|------|
| 打洞超时 | 自动降级 relay（静默，日志记录） |
| QUIC 握手失败（指纹不符） | 中止，报安全错误（绝不降级——指纹不符是安全问题） |
| UDP socket 绑定失败 | 直接降级 relay |
| relay 也失败 | 报错（现状行为） |

## 八、测试策略

- **单元测试**：UdpPuncher 打洞状态机（mock 收发、超时、成功）；QuicLink 证书指纹验证（不匹配拒绝）
- **双机实测**：100MB 数据 bioinfo7 ↔ Mac mini
  - 打洞成功 → QUIC 直连 → 验证 SHA-256 + 速率
  - 打洞失败（学校 NAT）→ 自动降级 relay → 验证仍成功
- **回退测试**：`FAN_NO_UDP=1` 环境开关禁用 UDP 打洞 → 确认纯 relay 路径仍工作
- **回归**：现有 transfer send/get/log 全部用例不回归
